Prompt engineering · Claude Opus 4.8

Opus 4.8 は 文字通りに読み、自分で加減する。

Claude Opus 4.8（model string claude-opus-4-8）は long-horizon な agentic 作業・ knowledge work・vision・memory に強い最新 Opus。4.7 のプロンプトはそのまま動くが、 応答の長さを自分でキャリブレートし、effort と adaptive thinking を厳密に尊重し、 指示を文字通り解釈するという 3 つの癖が前モデルとの差を生む。公式 prompting docs の 要点を、自分の手元（Claude Code on Opus 4.8）に効く順で整理する。

対象 claude-opus-4-8 出典 platform.claude.com / prompting best practices 確認日 2026-05-30 前モデル Opus 4.7 / 4.6 からの差分込み

核心の一文

Opus 4.8 を一言で表すと 「賢くなったが、勝手に気を利かせなくなった」。 前モデルでは曖昧な指示でも文脈から補完してくれたが、4.8 は書いてあることを書いてある通りにやる。 これは精度と再現性の向上だが、旧プロンプトの「察してくれる前提」が外れる。

4.8 の 3 つの癖（ここだけ覚える）

1. 長さを自己調整する ── 簡単な質問には短く、複雑な分析には長く。固定の冗長さを持たない。
2. effort と thinking を厳密に尊重する ── 特に low/medium では「言われたこと」にスコープを絞る。
3. 文字通り解釈する（literalism） ── 1 項目への指示を勝手に全項目へ一般化しない。やってない依頼を推測しない。

公式の表現では「4.7 のプロンプトでそのまま out of the box でよく動く」。つまり全書き換えは不要で、 挙動がズレた箇所だけピンポイントで調整するのが正しい付き合い方。以下のセクションは その「ズレやすい箇所」を効く順に並べたもの。

effort を最初のレバーにする

docs が繰り返し強調するのは 「プロンプトでこねる前に、まず effort を上げ下げしろ」。 effort は知能とトークン消費（=速度・コスト）のトレードオフを 5 段階で切るパラメータで、 4.8 はこれを過去のどの Opus よりも厳密に尊重する。

effort使いどころ注意
max知能最優先のタスクoverthinking 気味・リターン逓減あり
xhighコーディング / agentic のベスト出力トークン上限を大きく（64k〜）
high知能が要る用途の最低ライン知能とコストのバランス点
mediumコスト重視で知能を少し犠牲に難タスクで under-thinking のリスク
low短く scoped・低レイテンシ「言われたこと」だけやる。複雑題で浅くなる

複雑題で推論が浅いと感じたら プロンプトで回避せず effort を high / xhigh に上げる。 どうしても low に固定したい（レイテンシ要件）ときだけ、ターゲットを絞った一文を足す: 

This task involves multi-step reasoning. Think carefully through the problem before responding.

thinking — 4.8 ではデフォルト OFF

Opus 4.8 では thinking: {type: "adaptive"} を明示しない限り thinking は OFF。 adaptive thinking は effort とクエリ複雑度から「いつ・どれだけ考えるか」をモデルが動的に決める方式で、 旧 budget_tokens 方式（deprecated）より評価上も優秀。逆に「考えすぎ」を抑えたいときはこう steer する: 

Thinking adds latency and should only be used when it will meaningfully improve
answer quality — typically for problems that require multi-step reasoning.
When in doubt, respond directly.

API での書き方（extended thinking からの移行）

# Before（旧モデル: extended thinking + budget_tokens）
client.messages.create(
    model="claude-sonnet-4-5-20250929",
    max_tokens=64000,
    thinking={"type": "enabled", "budget_tokens": 32000},
)

# After（4.8: adaptive thinking + effort）
client.messages.create(
    model="claude-opus-4-8",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},  # max / xhigh / medium / low
)

max / xhigh では出力上限を大きく取る

effort を max / xhigh で回すなら、 subagent とツール呼び出しに跨って「考えて動く」余地を残すため max output token を 64k 起点で設定する。小さいと途中で切れる。

冗長さの自己調整と「文字通りの追従」

4.8 は応答長を「タスクの複雑さ」で自分で決める。固定の verbosity を持たないので、 プロダクトが特定のスタイル・長さに依存しているなら明示的にプロンプトで縛る必要がある。 冗長さを減らすなら: 

Provide concise, focused responses. Skip non-essential context, and keep examples minimal.

否定形より肯定形・実例

「〜するな」より「適切な簡潔さでこう書く」というポジティブな実例の方が効く。 これは 4.8 に限らない普遍則だが、literalism の強い 4.8 では特に差が出る。

literalism（文字通りの解釈）は 4.8 最大の挙動変化。1 つの項目への指示を黙って他項目へ 一般化せず、頼んでいない依頼を推測しない。利点は精度・再現性（構造化抽出やパイプライン向き）。 裏を返すと 「全体に適用してほしい」ならスコープを明示的に書く必要がある。

察してくれる前提（4.7 までの癖）

"Format the heading like this." と 1 例だけ示して全見出しに波及するのを期待する。4.8 は最初の 1 つだけ直すことがある。

スコープを明示（4.8 向け）

"Apply this formatting to every section, not just the first one." と範囲を言い切る。

トーンも再評価する

4.8 は direct で opinionated、追従的な前置き（validation-forward phrasing）と絵文字が控えめなのがデフォルト。 温かい・会話的な声が欲しいプロダクトは明示する: 

Use a warm, collaborative tone. Acknowledge the user's framing before answering.

ツール起動と並列呼び出し

4.8 は ツール呼び出しより推論を好む傾向がある（多くの場合これで結果が良くなる）。 もっとツールを使わせたいときの第一レバーも、やはり effort。 high / xhigh は agentic search / coding で明確にツール使用が増える。

加えて「行動させたい」なら指示を断定形に。 「can you suggest some changes（提案して）」だと提案だけで終わることがある。実際に編集させたいなら:

提案で終わりがち

Can you suggest some changes to improve this function?

行動する

Change this function to improve its performance.

並列ツール呼び出しを最大化する system prompt

4.8 は並列ツール実行が得意（複数検索・複数ファイル同時読み・bash 並列）。無指示でも成功率は高いが、 ほぼ 100% に寄せたいなら定番スニペット: 

<use_parallel_tool_calls>
If you intend to call multiple tools and there are no dependencies between the
tool calls, make all of the independent tool calls in parallel. Prioritize calling
tools simultaneously whenever the actions can be done in parallel rather than
sequentially. For example, when reading 3 files, run 3 tool calls in parallel.
However, if some tool calls depend on previous calls to inform dependent values,
do NOT call these tools in parallel and instead call them sequentially.
Never use placeholders or guess missing parameters in tool calls.
</use_parallel_tool_calls>

4.6/4.5 は「CRITICAL: MUST」を弱める

Opus 4.5 / 4.6 は system prompt への反応が強くなり、旧来の CRITICAL: You MUST use this tool when... のような強語が overtrigger（過剰起動）を招く。Use this tool when... 程度の普通の表現に落とす。

subagent と「過剰さ」の制御

ここは 世代で向きが逆なので要注意。Opus 4.6 は subagent を使いすぎる傾向（grep で十分な コード探索にまで subagent を spawn）。一方 4.8 はデフォルトで subagent を控えめにする。 どちらも prompting で steerable。

4.6: 使いすぎを抑える

"For simple tasks, single-file edits, or tasks where you need to maintain context across steps, work directly rather than delegating."

4.8: 使ってほしい時を明示

"Spawn multiple subagents in the same turn when fanning out across items or reading multiple files. Do not spawn a subagent for work you can complete directly."

overengineering（過剰設計）を抑える定番

4.5 / 4.6 は余計なファイル・抽象・「将来用」の柔軟性を作り込みがち。これも明示で抑える: 

Avoid over-engineering. Only make changes that are directly requested or clearly
necessary. Keep solutions simple and focused:
- Scope: Don't add features or "improvements" beyond what was asked.
- Documentation: Don't add docstrings/comments to code you didn't change.
- Defensive coding: Only validate at system boundaries (user input, external APIs).
- Abstractions: Don't create helpers for one-time operations. The right amount of
  complexity is the minimum needed for the current task.

テスト通過至上主義・ハードコードを禁じる

テストを通すことだけに最適化して一般解を諦める／test 入力専用のハードコードをする、を防ぐ一文も用意されている: "Implement a solution that works correctly for all valid inputs, not just the test cases. Tests are there to verify correctness, not to define the solution." 一時ファイルを散らかすなら "clean up these files at the end of the task." も足す。

frontend / design のデフォルト house style

4.8 には強い design の手癖がある: 暖色のクリーム/オフホワイト背景（約 #F4F1EA）、serif の display フォント（Georgia / Fraunces / Playfair）、 斜体の語アクセント、terracotta/amber のアクセント。editorial / hospitality / portfolio には映えるが、 ダッシュボード・dev tools・fintech・医療・エンタープライズには合わない。スライドにも出る。

「クリーム使うな」では直らない

このデフォルトは粘り強い。"don't use cream" や "make it clean and minimal" のような generic な否定は、別の固定パレットに移るだけで多様性は生まれない。効くのは次の 2 つ。

  1. 具体的な代替を指定する ── 4.8 は明示スペックを正確に守る。背景・アクセントの hex、角丸の px、フォントの性格（square / angular sans）、 セクション構成まで言い切る。色は #E9ECEC, #C9D2D4, #8C9A9E, #44545B, #11171B のようにパレットを列挙すると従う。
  2. 作る前に案を出させる ── これがデフォルトを壊す。かつて temperature で多様性を出していたなら、これに置き換える: 
Before building, propose 4 distinct visual directions tailored to this brief
(each as: bg hex / accent hex / typeface — one-line rationale).
Ask the user to pick one, then implement only that direction.

なお 4.8 は前モデルより少ない指示で AI slop を回避できる。長い frontend-design スニペットは不要になり、 次の短いタグで十分機能する: 

<frontend_aesthetics>
NEVER use generic AI-generated aesthetics like overused font families (Inter,
Roboto, Arial, system fonts), cliched color schemes (particularly purple gradients
on white or dark backgrounds), predictable layouts, and cookie-cutter design.
Use unique fonts, cohesive colors and themes, and animations for micro-interactions.
</frontend_aesthetics>

code review harness の罠 — recall が下がって見える

4.8 はバグ発見能力が実際に向上している（社内 eval で recall も precision も上）。 なのに旧モデル向けに調整した harness では recall が下がって見えることがある。 これは能力後退ではなく harness effect。

何が起きているか

プロンプトに 「high-severity だけ報告」「conservative に」「nitpick するな」と書いてあると、 4.8 はその指示を旧モデルより忠実に守る。バグは同じ深さで調査し見つけてはいるが、 自分の基準で「報告ラインを下回る」と判断したものを報告しない。 結果、precision は上がるのに、計測上の recall は落ちる。

対策は 「発見」と「フィルタ」を分けること。発見段階の仕事は coverage だと明示する: 

Report every issue you find, including ones you are uncertain about or consider
low-severity. Do not filter for importance or confidence at this stage — a separate
verification step will do that. Your goal here is coverage: it is better to surface
a finding that later gets filtered out than to silently drop a real bug. For each
finding, include your confidence level and an estimated severity so a downstream
filter can rank them.

1 パスで self-filter させるなら基準を具体化

important のような定性語ではなく 「incorrect behavior / test failure / misleading result を起こしうるバグは報告、pure style や naming の nit だけ除外」 のようにバーの位置を具体的に書く。eval のサブセットで recall / F1 を回して検証する。

※ これは CLAUDE.md のコードレビュー運用（汎用レビュアー + security-reviewer 並列起動）にも直結する。 各レビュアーの「発見」段階は coverage 重視で投げ、重み付け・棄却は呼び出し側で行うのが 4.8 に噛み合う。

長時間 agentic ワークと安全

4.8 は long-horizon の状態追跡が非常に強い。複数コンテキストウィンドウを跨いで 「作業 → state 保存 → 新しい窓で再開」ができる。これを活かす定石と、autonomy が上がった分の安全ガードを置く。

  • context awareness ── 残りトークン予算を自覚できる。harness が compaction するなら「途中で勝手に切り上げるな、限界前に state を memory へ保存せよ」と伝える。
  • state は構造化 + 自由記述の二段 ── テスト結果やタスク状況は tests.json 等の JSON、進捗メモは progress.txt の自由テキスト。git も state 追跡に強い。
  • マルチ窓では最初の窓を別扱い ── 1 窓目で枠組み（テスト・setup script）を作り、以降の窓で todo を回す。compaction より「新しい窓 + ファイルから state 復元」が有効なケースもある。
  • 検証ツールを与える ── 自律タスクが長くなるほど、人手フィードバック無しで正しさを確かめる手段（Playwright MCP / computer use）が要る。

autonomy が上がった分、破壊的操作にガードを

無指示だと 4.6 以降は「戻しにくい操作」「共有システムへの影響」（ファイル削除・force push・外部投稿）に 踏み込みうる。確認を挟ませたいなら明示する:

Consider the reversibility and potential impact of your actions. Take local, reversible actions freely (editing files, running tests), but for hard-to-reverse, shared-system, or destructive actions, ask the user first. Do not use destructive actions as a shortcut (e.g. --no-verify, discarding unfamiliar in-progress files).

リサーチ用途では「成功基準を定義」「複数ソースで裏取り」「競合する仮説を立て confidence を progress notes に記録し self-critique しながら hypothesis tree を更新」という構造化アプローチが推奨されている。

普遍の一般原則と prefill 廃止

モデル固有の癖を抜きにしても効く土台。Claude を「優秀だが文脈を知らない新入社員」と捉えるのが基本姿勢。 golden rule は「最小限の文脈しか持たない同僚にそのプロンプトを渡して、混乱するなら Claude も混乱する」。

  • 明確・具体的に ── 「above and beyond」が欲しいなら明示的に頼む。"Create an analytics dashboard. Include as many relevant features and interactions as possible." のように modifier を足す。
  • 動機を添える ── 「なぜそうしてほしいか」を書くと汎化が効く。"...read aloud by a text-to-speech engine, so never use ellipses..." のように理由付きが強い。
  • examples（few-shot） ── 出力の形・トーン・構造を steer する最も確実な手段。relevant / diverse に、<example> タグで囲む。3〜5 個が目安。
  • XML タグで構造化 ── instructions / context / input を別タグに分けると誤読が減る。
  • role を与える ── system に一文 role を置くだけで挙動とトーンが絞れる。
  • long context は「データを上、クエリを下」 ── 20k+ トークンでは長文を先頭、指示と質問を末尾に。最大 30% 改善の計測も。引用を先に抽出させると noise を切れる。

prefill は 4.6 以降サポート終了

最終 assistant ターンの prefill（応答の先頭を固定する手法）は Claude 4.6 以降で廃止（400 エラー）。 移行先は用途別に: 出力形式の固定 → Structured Outputs / 前置き除去 → system で "Respond directly without preamble." / 継続 → 中断テキストを user ターンに移す / 不当な refusal 回避 → 今は素の user プロンプトで十分。

出力整形は「するなより、する形を指定」。"Do not use markdown" より "Your response should be composed of smoothly flowing prose paragraphs."。 プロンプト自体の文体を出力したい文体に寄せる（markdown を減らしたいならプロンプトからも markdown を抜く）のも効く。 数式はデフォルト LaTeX なので、プレーンが欲しければ明示で止める。

手元（castle / Claude Code）への適用

この learnings を書いている環境そのものが Opus 4.8。docs の推奨と自分の設定がどう噛み合っているかを確認しておく。

覚えておく 1 行

4.8 で挙動がズレたら、まず effort を上げ下げ。プロンプトは「文字通り・スコープ明示・否定形より肯定実例」。 旧プロンプトの強語（CRITICAL/MUST）と「察してくれる前提」を外し、coverage とフィルタを分け、 autonomy には破壊的操作のガードを添える ── これだけで 4.7 以前の資産がそのまま 4.8 に乗る。
