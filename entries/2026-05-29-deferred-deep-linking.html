Deferred Deep Linking の仕組み

「リンクをタップ → アプリ未インストール → ストアでインストール → それでも狙った画面に着地する」。 この一見あたりまえの体験は、ストアがリンク情報をアプリに渡さないプライバシーの壁を、 プラットフォームごとに異なる手段で迂回することで成立している。その仕組みを、Android / iOS の 非対称性と Firebase Dynamic Links 終了（2025-08）後の現在地まで含めて分解する。

01

3行で言うと

Deferred Deep Linking（遅延ディープリンク, DDL）とは、 アプリを持っていないユーザーがリンクをタップしたとき、 インストールという「中断」を挟んでも、初回起動時に本来開きたかった特定の画面・コンテンツへ着地させる技術のこと。

  • 通常のディープリンクは「すでにアプリがあるユーザーを正しい画面へ」運ぶ。DDL は「これからインストールするユーザーを正しい画面へ」運ぶ — ここが決定的に難しい。
  • 難しさの正体はプライバシー境界。App Store / Play Store は「どのリンクから来たか」をインストール後のアプリに教えてくれない（指紋採取・追跡を防ぐための意図的な遮断）。
  • だから DDL は壁を迂回する。Android は OS 公式の Play Install Referrer（決定論的）。iOS は公式手段が無く、フィンガープリンティング（確率的）・クリップボード・App Clips を組み合わせる。

02

まず「3種類のリンク」を分ける

DDL を理解する前に、混同されがちな3つの概念を分離しておく。これらは積み重なった層であって、対立概念ではない。

種類解決する問題アプリの有無iOS / Android の実体
URL スキーム
myapp://item/42		 アプリ内の特定画面を開く（最古の方式） インストール済み前提 カスタムスキーム。未登録だと無反応・他アプリに乗っ取られうる
Universal Links / App Links
https://ex.com/item/42		 通常の https URL で直接アプリを開く（無ければ Web へ） インストール済み前提 iOS=apple-app-site-association, Android=assetlinks.json をドメインに置き OS が所有権を検証
Deferred Deep Link 未インストールユーザーを、インストール後に目的地へ 未インストールを扱う OS 標準機能では完結しない。referrer / fingerprint / clipboard で文脈を「運ぶ」

Universal Links（iOS）と App Links（Android）は「アプリが既にある」ケースの王道で、 どちらも HTTPS ドメインの所有権検証を土台にする。OS はリンクをタップした瞬間に 「このURLを処理できる検証済みアプリがあるか？」を確認し、あれば即アプリを開き、なければブラウザに落とす。

DDL はそのさらに上の層だ。「アプリが無いから、まずインストールさせる。でもインストール後に元の目的地を覚えておく」 — この「覚えておく」を OS が手伝ってくれないところに、すべての複雑さが宿る。

Universal Links 用 apple-app-site-association（ドメイン直下に配置）

{
  "applinks": {
    "apps": [],
    "details": [
      {
        "appID": "TEAMID.com.example.app",
        "paths": [ "/item/*", "/invite/*" ]
      }
    ]
  }
}
i

所有権検証 = なりすまし防止

AASA / assetlinks.json をドメインに置けるのは、そのドメインを管理できる人だけ。これにより「他人のドメインのリンクを横取りするアプリ」を OS レベルで防いでいる。DDL ベンダーが独自ドメイン（短縮URL）を要求するのもこの仕組みに乗るため。

03

核心の壁 — ストアはリンク情報を渡さない

DDL の本質的な課題はただ一つ。「リンクをクリックした事実」と「インストール後に初めて起動したアプリ」の間が、ストアによって意図的に分断されていること。

あなたがリンクをタップ → App Store / Play Store に飛ばされ → アプリをインストール → 起動する。 このとき、アプリは「自分がどのリンク経由でインストールされたか」を知らされない。 ストアは教えてくれないし、それは仕様だ。直接データを渡せてしまうと、 大規模なユーザー追跡・フィンガープリンティングの温床になるため、Apple も Google も意図的に塞いでいる。

したがって DDL の実装とは、突き詰めれば「この壁をどう迂回して、クリック時の文脈をインストール後のアプリへ運ぶか」の一点に尽きる。 そして運び方がプラットフォームによって大きく違う。ここに iOS / Android の非対称性が生まれる。

!

「ディープリンク」と「アトリビューション」は別物

文脈を運ぶ仕組みは、しばしば「どの広告経由でインストールされたか」を測るアトリビューション（後述の SKAdNetwork 等）と混同される。DDL はルーティング（どの画面に着地させるか）、アトリビューションは計測（どこから来たか）。同じ MMP SDK が両方を提供することが多いが、目的は分けて考えると整理しやすい。

04

Android — Play Install Referrer（決定論・OS公式）

Android には壁を越えるOS 公式の正規ルートがある。それが Play Install Referrer API だ。 Play Store 自身が referrer 文字列を保持し、インストール後にアプリの SDK がそれを取得できる。 マッチは推測ではなくほぼ 100% 正確（決定論的）になる。

仕組み

  1. クリック時

    リンク（広告）に一意の referrer パラメータ（click_id 等）を付与し、Play Store へ誘導。Store がこの値を一時保存する。

  2. インストール → 初回起動

    アプリ内の SDK が InstallReferrerClient で Play Store に接続し、保存された referrer を取り出す。

  3. 復元 → 着地

    取り出した click_id をバックエンドに問い合わせ、元の deep link 先を解決して目的画面へ遷移。

InstallReferrerClient（Kotlin）— 初回起動時に1回だけ呼ぶ

val client = InstallReferrerClient.newBuilder(context).build()
client.startConnection(object : InstallReferrerStateListener {
  override fun onInstallReferrerSetupFinished(responseCode: Int) {
    if (responseCode == InstallReferrerResponse.OK) {
      val details = client.installReferrer        // ReferrerDetails
      val referrer = details.installReferrer       // "utm_source=...&click_id=abc123"
      val clickTs  = details.referrerClickTimestampSeconds
      // → click_id を解決して目的画面へルーティング
      client.endConnection()
    }
  }
  override fun onInstallReferrerServiceDisconnected() { /* retry */ }
})
  • AIDL インターフェースとして実装される。Kotlin/Java からは Play Install Referrer Library でラップして使うのが標準。
  • referrer 情報は90日間保持され、再インストールしない限り変わらない。無駄な呼び出しを避けるため初回起動の1回だけ取得するのが定石。
  • 旧来の install_referrer ブロードキャスト Intent は廃止済み。Play Store はもうこの broadcast を送らない。
✓

Android が「楽な側」である理由

click_id を Play Store 自身が永続化してくれるので、確率マッチも時間窓も要らない。iOS で必要になる回りくどい迂回は、Android では基本的に不要。DDL の難しさは事実上「iOS をどうするか」の問題に集約される。

05

iOS — 公式 referrer が無い世界の3つの迂回

iOS には Install Referrer に相当する公式機構が存在しない。Apple は App Store をプライバシー境界として明確に扱う。 そのため DDL ベンダーは3つの迂回手段を、単独またはハイブリッドで使う。

(a) フィンガープリンティング — 確率的マッチング

最も歴史が長い方式。クリック時に環境の「スナップショット」（IP アドレス・User-Agent・デバイス機種・画面解像度・OS バージョン等の非識別シグナルの組み合わせ）を取り、 サーバーに保存する。ユーザーがインストールして初回起動すると、2枚目のスナップショットを端末側で取得。 両者を短い時間窓（典型的に 10分〜72時間）内で突き合わせ、一致信頼度が閾値を超えれば元のパラメータを引き渡す。

!

モダン iOS で精度が落ちている

App Tracking Transparency (ATT) が IDFA ベースのマッチングを制限し、iCloud Private Relay（iOS 15+）が iCloud+ ユーザーの IP アドレスを隠す。フィンガープリンティングの主軸だった IP マッチが Private Relay 下では機能しないため、確率方式単独の信頼性は年々下がっている。なお Apple のガイドライン上、10分・単回・非追跡の範囲なら Tracking には当たらないとされる運用が一般的。

(b) クリップボード — 決定論的マッチング

フィンガープリンティングが Private Relay で崩れる問題への回答。deep link そのものを端末のクリップボード（Universal Pasteboard）にコピーしておき、 インストール後の初回起動でアプリがそれを読み取る。ネットワーク識別子に一切依存しないため、Private Relay ユーザーでも確実に復元できる。Branch の NativeLink がこの代表例。

クリップボードから deep link を復元（Swift）

// アプリ初回起動時。UIPasteboard へのアクセスはユーザーに見える操作
if UIPasteboard.general.hasStrings {
  if let copied = UIPasteboard.general.string,
     let url = URL(string: copied),
     url.host == "ex.com" {          // 自分のドメインだけ採用
    router.deepLink(to: url)            // → 目的画面へ着地
    UIPasteboard.general.items = []     // 使い終えたら消す
  }
}
!

iOS のペースト通知・許可に注意

iOS 14 以降、アプリがクリップボードを読むと「○○が△△からペーストしました」というバナーが出る。iOS 16 以降は読み取り時にユーザー許可ダイアログが出ることもある。そのため実装では「アプリを入手（リンクをコピー）」のようなユーザーが明示的にコピーを選ぶ UXとセットにして、許可を自然に得る設計にする。hasStrings など detectPatterns 系 API で中身を読まずに存在判定する手も使われる。

(c) App Clips — Apple 公式の軽量アプリ

App Clips は、フルアプリをインストールせずに即起動できる軽量版アプリ。 DDL 文脈では「未インストール時に App Clip を起動してランディングとして使い、ユーザーがフルアプリを入手したら元の deep link を App Clip からフルアプリへ直接引き渡す」という流れを作れる。 IP に依存しないため Private Relay 対策として推奨されるが、クリップボード方式が1ステップで済むのに対し、App Clip は導入ステップが多いのがトレードオフ。

迂回手段確実性Private Relay 耐性主な難点
フィンガープリンティング確率的弱い（IP 隠蔽で崩れる）ATT / Private Relay で精度低下・時間窓の制約
クリップボード決定論的強いペースト通知・許可 UX の設計が必要
App Clips決定論的強い実装ステップが多い・App Clip 自体の整備

実運用ではこれらのハイブリッド（まずクリップボード、駄目ならフィンガープリンティングにフォールバック）が一般的だ。

07

計測フレームワークとの交差 — SKAN → AdAttributionKit

DDL（ルーティング）の隣には、Apple 公式のプライバシー保護型アトリビューション（計測）がある。直接の DDL 手段ではないが、密接に絡むので押さえておく。

SKAdNetwork (SKAN)

  • Apple 独自のアプリインストール計測フレームワーク（2018 登場）。デバイス識別子に頼らず、広告接触とインストールを結びつける。
  • iOS 14.5（2021）で ATT が導入され、IDFA が事実上使えなくなったことで、決定論的計測の唯一の正規手段として一気に主役化。
  • ポストバックは集計され遅延し、conversion value（最大63段階）でインストール後イベントを粗く伝える。個票は返らない。

AdAttributionKit (AAK) — WWDC 2024 の後継

SKAN を土台に拡張した新フレームワーク。両者は相互運用可能で当面は共存する。DDL と交差するのは特に 再エンゲージメントだ。

  1. 複数ストア対応

    EU の Digital Markets Act 対応として iOS 17.4（2024-03）で代替ストアにも対応。どこから入れたかを示す marketplace identifier を持つ（SKAN には無い）。

  2. 再エンゲージメント（DDL との接点）

    eligible-for-re-engagement を立てた広告を、既にアプリを持つユーザーがタップすると、Universal Link でアプリを開き、リンク先の画面へ誘導。Universal Link 経由なら最大35日のコンバージョン計測が可能。

  3. 厳格化と検証

    全インプレッションを JWS（JSON Web Signature）で署名必須。2秒以上視聴された広告のみカウント。Developer Mode で時間ランダム化を外し、検証を高速化できる。

i

SKAN の廃止予定は「無い」

2026年5月時点で、Apple は SKAdNetwork の廃止時期を発表していない。AAK は「いずれの後継」と位置づけられつつ、当面は SKAN と並走する。アトリビューションが両方走るときは「直近にタップした広告」優先、タップが無ければ「直近に視聴した広告」優先で、クリックスルーがビュースルーに勝つ。なお AAK には Safari 向けの Web AAK（Private Click Measurement の後継）もある。

08

エコシステム 2025–2026 — FDL 終了と代替

DDL の現実的な選択は、2025年8月に大きく動いた。長年「無料の定番」だった Firebase Dynamic Links (FDL) が 2025-08-25 に完全終了したのだ。

  • 終了後、FDL のリンク（独自ドメイン・*.page.link 双方）はHTTP 404を返す。新規リンク作成も不可。page.link サブドメインは消滅した。
  • FDL の分析データは終了日までにエクスポートしなかった分は復元不能。多くのチームが移行を迫られた。

移行先の主な選択肢

選択肢立ち位置こんなチームに
Branchディープリンク特化（計測は別途）DDL / web-to-app が主目的。FDL の最も素直な後継
AppsFlyer (OneLink)フル MMP + 強力な DDL有料 UA を回し、計測も一体で欲しい大規模チーム
Adjustフル MMP（プライバシー計測に強い）EU/APAC 等の規制環境で計測を重視
Dub / ChottuLink 等軽量・FDL の 1:1 代替系計測は不要、リンクだけ欲しい小〜中規模
自前 (Universal Links + 独自サーバー)第三者依存ゼロフルコントロール志向。ただし DDL 部分（clipboard 等）は自作が必要
!

「計測が要るか」で選ぶ

FDL ユーザーの多くは計測（アトリビューション）を使っていなかった。「ディープリンクが欲しいだけ」なら、フル MMP（AppsFlyer / Adjust）は重すぎる。逆に有料広告を回すなら MMP 一体型が効く。Universal Links だけの自前構成は依存ゼロだが、未インストール時に目的画面へ飛ばすロジック（clipboard / Pasteboard でパラメータ保存）は OS が用意してくれない点に注意。

09

実装の勘所とまとめ

最後に、DDL を実装・選定するときに効く要点を凝縮しておく。

  • iOS / Android の非対称性を前提に。 Android は Install Referrer でほぼ解決。難しさは iOS に集中する。
  • iOS はハイブリッドが現実解。 Private Relay 耐性のあるクリップボード / App Clip を主軸に、フィンガープリンティングをフォールバックに。
  • 時間窓を意識する。 フィンガープリンティングは 10分〜72時間の窓でしか当たらない。インストールが遅いと取りこぼす。
  • クリップボードは UX とセット。 ペースト通知・許可ダイアログを「コピーして続行」の自然な流れで吸収する設計に。
  • ルーティングと計測を分けて考える。 「どの画面へ」(DDL) と「どこから来たか」(SKAN/AAK) は別レイヤー。混ぜると要件が膨らむ。
  • ドメイン所有権が土台。 Universal Links / App Links は AASA / assetlinks.json が正しく配信されていることが大前提。ここが崩れると全部ブラウザに落ちる。
✓

一文でまとめると

Deferred Deep Linking とは「ストアが意図的に作ったプライバシーの壁を越えて、クリック時の文脈を初回起動のアプリへ運ぶ」技術。Android は OS 公式の Install Referrer で決定論的に、iOS は公式手段が無いためフィンガープリンティング・クリップボード・App Clips を組み合わせて越える。FDL 終了後は Branch / AppsFlyer / Adjust / 軽量系から、計測の要否で選ぶ。
