自分のドッグフードを 食べる。

Dogfood / dogfooding は「自分たちで作ったソフトウェアを、自分たち自身が daily user として使う」 ソフトウェア開発文化のキーワード。単なる社内テストではなく、品質責任とフィードバックループの 両方を内包する独特の語彙です。1988 年 Microsoft の社内メモが起点で、今では Apple / Google / Anthropic も含めた業界共通語になっています。

01

核心の一文

definition

「自分が daily に使う気にならないものを、顧客に売るな」 ── これが dogfooding の哲学。テストプロセスではなく、品質責任のスタンスを指す言葉です。

i

1 行で言うと

"Eating your own dog food" = 自社が作ったドッグフードを、 自社の人間が食べる。比喩としては「ペットフード会社の社長が、自社製品を自分の犬に 食べさせられるか？」という品質確認の文化。

02

語源 — 1988 年の Microsoft メモ

history

この言葉が IT 業界に定着したのは 1988 年 7 月。Microsoft の Paul Maritz が Brian Valentine（当時 LAN Manager の Test Manager）に送った社内メールが起点とされています。

"

原文（要約）

"We are going to start eating our own dog food." ── LAN Manager の社内利用を徹底し、自社で使い込むことで品質を底上げしようという呼びかけ。 "Eating dog food" の比喩自体はそれ以前から英語イディオムとして存在していたが、 ソフトウェア業界での文脈はこの社内メモが起源。

その後 1990 年代の Microsoft 内部文化で広まり、Bill Gates の社内スピーチや Windows / Office の開発プロセスでも使われるようになりました。2000 年代以降は Google / Apple / Mozilla を含む業界全体の共通語に。Anthropic も Claude を 社内コーディングに使い込む文化を持っており、これも典型的な dogfooding です。

03

なぜ単なる QA ではなく "文化" なのか

motivation

dogfooding は QA テストと似ているようで、目的・関与のされ方が違います。テストが「仕様の照合」 なら、dogfood は「unfiltered な使用感の獲得」。3 つのレイヤーで効きます。

  1. 品質の自己検証 ── テストケース・ドキュメント・スクリーンショットでは見えない「微妙な使いにくさ」は、 daily user になって初めて気付く。3 クリックで済むはずが 5 クリックかかる、エラーメッセージが 読みにくい、起動時間が体感で重い、etc.
  2. コミットメント表明 ── 「自分で使う気にならないツールを他人に勧めない」という品質責任の比喩。 「dogfood してるか？」は「君は本気でこれが良いと思っているか？」の業界スラング。
  3. 早期フィードバックループ ── 外部ユーザーに出す前に、開発者自身が体験する。バグの "発見 → 修正" の往復が同じ人の頭の中で 完結するため、issue tracker を経由するより圧倒的に速い。
04

alpha / beta との位置関係

layering

"Testing の段階" は俗称が乱立しがちですが、ざっくり次のような階層で語られます。 dogfood は alpha と beta の間に位置するのが標準的な理解です。

段階 使う人 主な目的 典型的な品質
alpha 開発チーム数人 動くか確認 クラッシュ前提
dogfood 社員全員 / 開発組織全体 daily 使用に耐えるか 業務で使える程度
beta (closed) 選ばれた外部ユーザー 外部視点の検証 機能ほぼ確定
beta (open) 希望する一般ユーザー スケール検証 細部の磨き込み
release 全ユーザー 公式提供 SLA を満たす
✓

覚え方

alpha = 開発者だけ / dogfood = 自社全員 / beta = 外部。 dogfood は「品質はまだ甘いかもしれないが、社内の人間が我慢して使うことで 次の品質ジャンプを買う」段階。

05

反対概念 — "Drink your own champagne"

contrast

Dogfood の "犬のエサ" という比喩は「妥協を許容する」ニュアンスがあります。これに対して "Drink your own champagne"（自社のシャンパンを飲め）は同じことを ポジティブに言い換えた、より洗練された言い回し。意味はほぼ同じです。

Dogfood

「不味くても食べる」ニュアンス。品質責任の比喩として粗削り。 開発組織内部での自虐的・実務的な用法に向く。

Champagne

「美味いものは自分でも味わう」ニュアンス。マーケティング寄りで美しい。 外向き・経営層向けに言い換えるときに使われる。

実際の開発現場では dogfood の方が圧倒的に多用されます。 「シャンパン飲んでるか？」よりも「dogfood してるか？」の方が、 開発者間の正直な品質ディスカッションに馴染むため。

06

アンチパターン

pitfalls

dogfooding が 儀式化すると本来の効果が失われます。よくある失敗:

  1. "使う" だけで報告しない ── 社内に配って終わり。フィードバックを集める仕組み (Slack channel / issue template) が無いと、せっかくの気付きが揮発する。
  2. 開発チームしか使わない ── 自分が作ったものは盲点が多い。営業 / サポート / デザイン部門など、 開発と異なる視点を持つメンバーが触ってこそ価値がある。
  3. dogfood が外部リリースの代替になる ── 「社内で使ってるから問題ない」と過信するパターン。社内環境は ネットワーク・端末・ユースケースが偏っているため、外部 beta も必須。
  4. 不便を黙って我慢する ── 「自分が作ったから文句言いにくい」が働くと、本当の使い勝手が 可視化されない。匿名フィードバックの仕組みがあると緩和される。
  5. dogfood 用の "特別なビルド" を作る ── 社内用に機能やデバッグログを増やしたビルドを配ると、 外部リリースと挙動が変わってしまい dogfooding の意味が消える。 原則として外部公開と同じバイナリを使う。
07

castle 文脈での dogfood

applied

自分用 dotfiles リポジトリ castle は典型的な dogfooding 環境です。 自作スキル・自作 nix-darwin 構成・自作 Hammerspoon マクロを 自分の daily 開発機で 実際に使い倒すことで、品質と運用ノウハウが蓄積されます。

  • scripts/publish-claude-skills.sh のホワイトリスト方式 ── 「dogfood 済み skill のみを社内 GHE marketplace に配布」という設計。 自分で日常使いに耐えたものだけが社内配布の opt-in リストに昇格する。
  • 新規スキルは PUBLISH_SKILLS リストに手動追加 ── 自動配布しない。手動 opt-in にすることで「これは本当に使い込んだか？」の 自問が必ず入る安全装置。
  • CLAUDE.md / docs/ の蓄積 ── 自分が踏んだ罠 (ex. cmux の theme 状態問題 / Xcode font cache) を docs/ にメモする習慣自体が dogfooding の副産物。
i

逆方向の落とし穴

自分専用環境を作り込みすぎると 他人の環境で動かない 落とし穴がある。 castle が machine-local 部分 (op://, .gitconfig.local) を切り出しているのは、 dogfooding を続けながらも他人 / 他マシンで再現できる構造を保つため。
