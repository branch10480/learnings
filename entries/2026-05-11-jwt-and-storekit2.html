Auth deep-dive · iOS · 2026

JWT は 3 つの Base64 をドットで繋いだ署名つきトークン。

JWT (JSON Web Token, RFC 7519) は header.payload.signature という たった 3 ピースの自己完結トークン。StoreKit 2 はこの仕組みを丸ごと採用し、 旧来の「不透明なレシート文字列」を JWS 署名済みトランザクションへ置き換えた。 ここでは JWT 自体の構造から、StoreKit 2 が JWT に依存している 2 つの方向（受信/送信）まで通読する。

RFC 7519 (JWT) · 7515 (JWS) · 7518 (JWA) StoreKit 2 (iOS 15+, 2021) 関連 OAuth 2 · OIDC · ES256 Apple API App Store Server API / V2 Notifications

JWT とは何か

JWT は 「JSON で書かれた主張（claims）に、暗号署名をつけて Base64URL で 3 つ並べたもの」。 暗号化ではなく「改竄検知」が主目的で、ペイロードは誰でも復号せずに読める。これを混同すると パスワードを payload に入れるなどの致命的な誤用に繋がる。

核心の一文

「JWT は秘密ではなく、改竄されていない事実」を運ぶ封筒。 内容は誰でも読める（payload は Base64URL のまま）が、 署名を持っている発行者の意志でのみ作れることが暗号的に保証される。

構造の解剖

JWT は ASCII 文字列 1 本だが、ドットで 3 つに分かれる。それぞれ Base64URL（パディング無し）で エンコードされた JSON（あるいはバイト列）。実物を切り分けて、何が入っているか具体的に見る。

実例（短く加工）

eyJhbGciOiJFUzI1NiIsImtpZCI6IjBYNzZBQiJ9.eyJpc3MiOiJBcHBsZSIsInN1YiI6ImNvbS5leGFtcGxlLmFwcCIsImV4cCI6MTcxOTAwMDAwMH0.MEUCIQDxr2...JzG9w

分解して JSON にすると

// 1. header — 署名アルゴリズム + 鍵 ID
{
  "alg": "ES256",
  "kid": "0X76AB"
}

// 2. payload — claims（主張）の集合
{
  "iss": "Apple",            // issuer
  "sub": "com.example.app",  // subject
  "exp": 1719000000           // expiration (epoch)
}

// 3. signature — header と payload の Base64URL を "." で結合した
//    バイト列に対する暗号署名（バイナリ → Base64URL）
sign(privateKey, base64url(header) + "." + base64url(payload))
セグメント内容暗号化？改竄検知？
headeralg, kid, typ などNoYes（署名対象）
payloadclaims（任意の JSON）NoYes（署名対象）
signatureHMAC または公開鍵署名—Yes（自身が証拠）

誤解しやすい点

JWT 単体では 暗号化されていない。Base64URL は変換であって暗号化ではない。 payload を秘匿したければ JWE（後述）を使うか、JWT を HTTPS 上でしか流さない設計にする。

署名アルゴリズム

署名は対称鍵（HMAC 系）と非対称鍵（RSA, ECDSA, EdDSA）に大別される。Apple の世界では ECDSA の ES256（P-256 + SHA-256）がほぼ統一的に使われる。 理由は鍵が短く、署名も短く、CPU コストが低いため。

alg正式名鍵の種類典型用途
HS256HMAC-SHA-256対称（共有秘密）サーバー内部の短命トークン
RS256RSASSA-PKCS1-v1_5 + SHA-256非対称 RSA 2048+OIDC ID トークン（多くの IdP）
PS256RSASSA-PSS + SHA-256非対称 RSA新しい OIDC 実装
ES256ECDSA P-256 + SHA-256非対称 ECApple StoreKit 2 / Sign in with Apple
ES384ECDSA P-384 + SHA-384非対称 ECより強い保証が必要なとき
EdDSAEd25519 / Ed448非対称 EC新しい設計（Apple は未採用）
none署名なし—絶対に受け入れない（後述）

なぜ Apple は ES256 なのか

P-256 公開鍵は 64 byte、署名は 64 byte（DER 形式だと約 70 byte）。 RSA 2048 は鍵 256 byte / 署名 256 byte。スマホ間でやり取りするトランザクションの JWT には、サイズと CPU コストの両面で EC が圧倒的に有利。 Sign in with Apple, APNs Auth Token, App Store Connect API も同じ ES256。

JWS / JWE と JWT の関係

ここがよく混乱する箇所。JWT は「中身（claims セット）の規格」、JWS は「署名形式の規格」、 JWE は「暗号化形式の規格」。普段「JWT」と呼んでいるのはほぼ常に「JWS で署名された JWT」。 StoreKit 2 のドキュメントが「JWS Compact Serialization」と書いているのも、結局は同じもの。

  • JWT は中身（claims）。普通は JWS でラップして送る。
  • JWS は署名形式。header.payload.signature の Compact Serialization が一般的。
  • JWE は暗号化形式。header.encrypted_key.iv.ciphertext.tag の 5 ピース。
  • JOSE はこれらをまとめた IETF Working Group。

標準 Claims と独自 Claims

payload に入れるキーは何でも好きにできるが、相互運用のために 登録済み（Registered）Claims が決まっている。短い 3 文字キーが使われるのは「ヘッダの上で送られる前提でサイズを切り詰めたい」から。

Public Claim を新たに登録するか、URI 形式（"https://example.com/role"）で Private Claim を使う。短い英単語をそのまま claim キーにするのは、将来の標準と衝突する地雷。

JWT の有名な落とし穴

JWT のセキュリティ問題はほとんど「実装の手抜き」由来。標準仕様に沿って検証していれば普通は安全だが、 以下は 実際に CVE になった事例のあるパターン。検証ライブラリを書く・選ぶときに見るべき。

  1. alg: none を受け入れる。RFC 上は許されているが、攻撃者が任意の payload を作れる。 検証側は 受け入れる alg を allowlist で固定する（例：ES256 のみ）。
  2. HS256 ↔ RS256 confusion。サーバーが alg を信用して 「RSA 公開鍵」を HMAC の鍵として使うと、攻撃者は公開鍵を入手して署名を捏造できる。 alg はライブラリに渡さず、検証側で固定する。
  3. kid のディレクトリトラバーサル。kid を SQL クエリやファイルパスにそのまま使うと、 ../ や SQL injection を許す。kid は 許可された値のみ参照。
  4. jku / x5u を信用する。攻撃者が任意の URL を入れて自分のサーバーから公開鍵を返せる。 これらヘッダを尊重しないか、ホスト名を allowlist する。
  5. exp を検証しない。「読めて claims が取れたから OK」とする実装は永久トークンを生む。
  6. 署名前にデコードした payload を信用する。decode → 検証 と verify → デコードは別物。後者を必ず使う。
  7. 大きすぎる JWT を Cookie に入れる。HTTP ヘッダ上限（8KB 程度）を超え、 リクエストが落ちる。session cookie + サーバー側の状態のほうが楽な局面は多い。

Apple の検証で具体的に守るもの

StoreKit 2 の VerificationResult は OS が以下を全部チェック済みで返す： (1) ヘッダ alg = ES256、(2) x5c の証明書チェーンが Apple Root CA に至る、 (3) 署名検証、(4) bundleId が自アプリと一致、(5) exp 検証。 ただし environment と originalTransactionId のリプレイ検知はアプリ側責任。

なぜ StoreKit 2 が JWT に乗り換えたか

この移行は単なる「フォーマット変更」ではなく、「検証アーキテクチャ自体の作り直し」。 旧方式が抱えていた往復コスト（latency / 可用性 / 実装複雑度）を一行ずつ潰していくと、 なぜ JWS が選ばれたかが自然に見えてくる。ここでは旧フローと新フローを並べて具体的に比較する。

▍旧フロー: PKCS#7 レシート + verifyReceipt 往復

▍新フロー: JWS をローカル検証（往復ゼロ）

▍旧 StoreKit (legacy receipt)

  • レシートは PKCS#7 署名された不透明バイナリ → Base64（4–60 KB）
  • 中身を確認するには Apple の /verifyReceipt を毎回叩く必要
  • レシートには 累積で全購入が入る → サブスク履歴が長いほど巨大化
  • Sandbox / Production の取り違えを 21007 / 21008 で再試行
  • shared secret（App-Specific Shared Secret）を Bundle ID ごとに保管・流出リスク
  • クライアントだけでは検証完結しない（PKCS#7 を自前パースは現実的でない）

▍StoreKit 2 (JWS Signed Transaction)

  • 各トランザクションが 独立した JWS（典型 1.5–3 KB）で返る
  • x5c ヘッダに証明書チェーンが内蔵 → 単独で検証完結
  • Apple Root CA G3 はあらかじめ持っているだけで足りる（再ダウンロード不要）
  • 環境は payload の environment 文字列で自明（21007 ループ消滅）
  • 共有秘密の概念がない（公開鍵検証のみ）
  • クライアントもサーバーもまったく同じ検証ロジックでよい（対称性）

▍往復コストの定量比較

観点旧（verifyReceipt）新（JWS ローカル）
クライアント → 自社1 RTT1 RTT（変わらず）
自社 → Apple1〜2 RTT（21007 リトライで 2）0 RTT
Apple 側のレイテンシ依存あり（数百 ms 〜稀に数秒、障害時は数十秒）なし
検証可否がネットワークに依存ありなし（オフラインでも検証可）
Apple サーバー障害時ユーザーが課金できない / 機能が解放されない影響なし（既受領 JWS は手元で検証可）
転送ペイロード（更新時）累積レシート全体（最大 60 KB+）新規 1 件分の JWS（約 2 KB）
サーバー側の依存Apple の verifyReceipt API + shared secret 管理Apple Root CA 1 枚のみ（PEM 数 KB）
環境判定21007 を見て Sandbox URL に張り直すpayload.environment で即判定

旧方式が痛かった現場の典型

(1) Apple の verifyReceipt が混雑していて 30 秒返ってこない → ユーザーから見ると「課金は通ったのに有料機能が解放されない」となる。 (2) 検証直後に Sandbox/Production の判定を間違えて 21007 ループ → 審査時とリリース時で挙動が違うバグの温床。 (3) shared secret の取り扱い → これが漏れると他人が 勝手に verifyReceipt を叩けてしまう。鍵管理コストが純増する。 JWS はこれら全部を「公開鍵検証 + ローカル」で消した。

結局のところの設計利益

「Apple のオンラインエンドポイントに依存しない」ことが核心。 JWS は「Apple が秘密鍵で署名した事実」をバイト列に閉じ込めているので、 一度受け取ってしまえばインターネットが切れていても検証できる。 iOS デバイス・自社サーバー・社内バッチの 3 者が同じ検証ロジックを共有でき、 障害ドメインが「自社 + Apple Root CA を信用する」だけに縮む。

補足: App Store Server API は今も生きている

「往復が消えた」と言ったが、それは 検証の往復の話。 購入履歴の検索・返金検知・サブスク状態の確認などは今でも api.storekit.itunes.apple.com を叩く。 ただしレスポンスは JWS なので、受信したら その場でローカル検証でき、 返ってきたデータの真正性を Apple との追加往復なしで確認できる。

JWS Signed Transaction の中身

Transaction.currentEntitlements や Product.purchase() から 返ってくる VerificationResult<Transaction> は、内部に jwsRepresentation: String を持つ。これがまさに JWS 形式の JWT。

jwsRepresentation を分解した header

{
  "alg": "ES256",
  "x5c": [
    "MIIE...leaf cert...",           // (1) 末端: WWDR が署名
    "MIIE...intermediate G6...",    // (2) 中間: WWDR G6
    "MIIC...Apple Root CA - G3"     // (3) 根: 既知の Apple Root
  ]
}

payload（Transaction の主要フィールド）

{
  "transactionId":         "2000000400000001",
  "originalTransactionId": "2000000300000099",
  "webOrderLineItemId":   "2000000099999999",
  "bundleId":              "com.example.app",
  "productId":             "com.example.app.pro.month",
  "subscriptionGroupIdentifier": "21000000",
  "purchaseDate":          1736900000000,
  "expiresDate":           1739492000000,
  "quantity":              1,
  "type":                  "Auto-Renewable Subscription",
  "inAppOwnershipType":    "PURCHASED",
  "environment":           "Production"
}

signedDate と nonce

payload には signedDate も入る。Apple が JWS に署名した時刻で、 古いトランザクションがリプレイされていないかを判定するヒントになる。 高セキュリティ用途では、payload の appAccountToken や deviceVerification を使ったアンチリプレイも組む。

x5c と Apple Root CA

JWS のヘッダにある x5c（X.509 Certificate Chain）は、 「この署名を作った公開鍵が、信頼できる根まで辿れること」を証明する証明書チェーン。 RFC 7515 §4.1.6 で定義された JOSE 標準ヘッダ。Apple は配列の末尾を Apple Root CA - G3 にしてくる。

  1. x5c[0] の公開鍵で JWS の署名を検証（ペイロードが改竄されていないことを確認）。
  2. x5c[0] が x5c[1] によって署名されているか確認（leaf → intermediate）。
  3. x5c[1] が x5c[2] によって署名されているか確認（intermediate → root）。
  4. x5c[2] が事前に持っている Apple Root CA - G3 と一致するか（最重要）。 ここを「ヘッダにある最後の証明書を信用する」と書くと崩壊する。事前に焼き込んだ root と完全一致を確認する。
  5. 各証明書の有効期限・失効を確認。OS 任せでも良いが、 サーバー側ライブラリを書くなら明示的にやる必要がある。

App Store Server API への JWT

ここまでの JWT は「Apple が発行 → アプリが受け取って検証」の流れ。 逆に App Store Server API をサーバーから叩くときは、 自分が ES256 の秘密鍵を使って JWT を作り、Authorization: Bearer として送る。 JWT は両方向で使われる。

App Store Server API への認証 JWT

// header
{
  "alg": "ES256",
  "kid": "ABC123DEFG",        // 鍵 ID（App Store Connect で発行）
  "typ": "JWT"
}

// payload
{
  "iss": "57246542-96fe-1a63-e053-0824d011072a",  // Issuer ID
  "iat": 1736900000,
  "exp": 1736903600,                       // 最大 1 時間（API ガイドラインより）
  "aud": "appstoreconnect-v1",            // 必須 (App Store Server API)
  "bid": "com.example.app"                  // Bundle ID
}

// 署名は App Store Connect でダウンロードした .p8（ES256 秘密鍵）で行う

App Store Server Notifications V2

課金状態が変化した（更新成功・解約・返金など）ときに、Apple は登録された URL に POST してくる。V1 は不透明な JSON だったが、V2 は signedPayload という単一の JWS 文字列のみ。 サーバー側で StoreKit 2 と同じやり方で検証する。 

// Apple から飛んでくる POST body（V2）
{
  "signedPayload": "eyJhbGciOiJFUzI1NiIsIng1YyI6Wy..."
}

// signedPayload を JWS としてデコードした payload
{
  "notificationType":  "DID_RENEW",
  "subtype":           "BILLING_RECOVERY",
  "notificationUUID":  "ce7b1a2b-...",    // 重複検知に使う
  "version":           "2.0",
  "signedDate":        1736901234567,
  "data": {
    "appAppleId":               1234567890,
    "bundleId":                 "com.example.app",
    "environment":              "Production",
    "signedTransactionInfo":    "eyJhbGc...",    // ★ 入れ子 JWS
    "signedRenewalInfo":        "eyJhbGc..."     // ★ 入れ子 JWS
  }
}

JWS が入れ子になっていることに注意

外側の signedPayload をまず検証して payload を取り出す。 すると中に signedTransactionInfo という別の JWS 文字列が入っており、 それも個別に検証する必要がある。1 つの通知の検証は最低 2 回の JWS 検証になる。

notificationType の主なバリエーション

  • SUBSCRIBED / DID_RENEW — 有効な状態が継続
  • DID_FAIL_TO_RENEW — 課金失敗（subtype=GRACE_PERIOD なら猶予期間）
  • DID_CHANGE_RENEWAL_STATUS — ユーザーが自動更新オフ/オン
  • DID_CHANGE_RENEWAL_PREF — プラン変更（即時/期末）
  • EXPIRED — 期限切れ
  • REVOKE / REFUND — 取り消し（即座に entitlement を切る）
  • CONSUMPTION_REQUEST — 返金時に「使用量データ」を Apple に返す機会

Swift で検証する

iOS / macOS 上では VerificationResult が OS 任せで楽。 サーバー側 Swift では Apple が公開している app-store-server-library-swift か、 汎用 JOSE ライブラリ（JWTKit 等）を使う。両方の最小例。

クライアント (StoreKit 2)

for await result in Transaction.currentEntitlements {
  switch result {
  case .verified(let transaction):
    // OS が JWS の署名・x5c・bundleId・exp を検証済み
    // あとはアプリ側で originalTransactionId のリプレイ等を担保
    grantEntitlement(productId: transaction.productID)
    await transaction.finish()

  case .unverified(let transaction, let error):
    // 署名検証に失敗 — 絶対に entitlement を与えない
    log("Untrusted: \(error)")
  }
}

サーバー (Vapor + JWTKit, ES256)

import JWTKit

// 1. signedPayload（外側）を検証
struct NotificationPayload: JWTPayload {
  var notificationType: String
  var signedDate: Int
  var data: DataField
  struct DataField: Codable {
    var bundleId: String
    var environment: String
    var signedTransactionInfo: String?
  }
  func verify(using signer: JWTSigner) throws { /* 業務固有チェック */ }
}

let jws = req.body.signedPayload
let headerJSON = try decodeHeader(jws)
let chain = headerJSON.x5c.map { Certificate(base64: $0) }

// 2. x5c を Apple Root CA まで検証
try AppleCAValidator.shared.validate(chain: chain)

// 3. leaf の公開鍵で JWS を検証
let signer = JWTSigner.es256(key: try .public(pem: chain[0].publicKeyPEM))
let outer = try signer.verify(jws, as: NotificationPayload.self)

// 4. 入れ子の signedTransactionInfo も同じ手順で検証
if let inner = outer.data.signedTransactionInfo {
  let tx = try verifyTransactionJWS(inner)
  applyEntitlement(tx)
}

本番では公式ライブラリ

Apple の app-store-server-library（Swift / Java / Python / Node / Go）が 上記の x5c 検証 + 失効チェック + 環境判定を全部やってくれる。自前で書くのは学習目的でだけ。

まとめ

  • JWT = Base64URL(header).Base64URL(payload).署名。 中身は読める、改竄はできない。Apple は ES256 一択。
  • StoreKit 2 はレシート文字列を捨てて、購入トランザクションを JWS（=JWT）で返すようになった。 x5c で Apple Root CA まで連鎖検証できるので、サーバーに往復しなくても信用できる。
  • App Store Server API / Notifications V2 は逆方向の JWT。 自分で ES256 の .p8 で JWT を作って Bearer 認証する側でもあり、 受信側でも JWS を検証する側でもある — JWT が言語の共通プロトコルになっている。
