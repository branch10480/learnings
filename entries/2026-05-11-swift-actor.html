Language deep-dive · Swift 5.5+

Actor は キューを内蔵した参照型である。

Swift 5.5 で導入された actor は、class でも struct でもない第三の参照型。 内部状態へのアクセスを自動的にシリアライズすることで、データ競合（data race）を コンパイル時に防ぐ。本ドキュメントは「なぜ class では駄目だったのか」から Reentrancy の落とし穴まで、段階的に解説します。

導入 Swift 5.5 (2021) 関連 async / await · Sendable 提案 SE-0306 Concurrency strict mode Swift 6

Actor とは何か

Actor は "状態を持つ + 状態への並行アクセスを自動でシリアライズする" 参照型。 class とほぼ同じ書き心地でありながら、複数のスレッド（タスク）から同時に状態を弄っても 壊れないことが コンパイル時に保証される。背景にあるのは Erlang や Elixir で 古典的に使われている「アクターモデル」の考え方です。

核心の一文

「Actor とは、内部状態へのアクセスが自動的に直列化される class」 と理解するのが最短ルート。あとはこの "自動的に直列化" がどうコンパイラと ランタイムで実現されているかを掘っていきます。

なぜ Actor が必要だったか

class の参照を複数のスレッドから同時に触ると、容易に壊れます。これが data race（データ競合）。Swift 6 以前では、これを防ぐのは開発者の責任で、 DispatchQueue やロックを手動で書く必要がありました。

❌ 危険な class

final class Counter {
  var count = 0
  func increment() {
    count += 1   // data race 候補
  }
}

let c = Counter()
// 別々のスレッドから:
DispatchQueue.global().async { c.increment() }
DispatchQueue.global().async { c.increment() }
// → count が 1 になることもある（壊れる）

✅ 安全な actor

actor Counter {
  var count = 0
  func increment() {
    count += 1   // 自動でシリアライズ
  }
}

let c = Counter()
await withTaskGroup(of: Void.self) { g in
  g.addTask { await c.increment() }
  g.addTask { await c.increment() }
}
// → count は必ず 2 になる

手動排他制御との比較

方式記述量デッドロック耐性コンパイル時保証
手動 NSLock多い低（簡単に発生）無し
DispatchQueue (serial)中中無し
os_unfair_lock少（だが落とし穴多）低無し
actor最少高あり

actor の最大の価値はコンパイル時保証

DispatchQueue やロックは「ちゃんと使えば」安全ですが、間違いはコンパイラに見えません。 actor は data race の可能性をコンパイル時に検出する仕組みなので、 「コードレビューで見落とした並行性バグ」が原理的に減ります。

基本構文

宣言は class を actor に 置き換えるだけ。プロパティ・メソッド・イニシャライザの書き方は class と同じ。 違いは「外から状態にアクセスするには await が必要になる」ことだけ。 

actor BankAccount {
  private(set) var balance: Int
  private var transactions: [Transaction] = []

  init(initialBalance: Int) {
    self.balance = initialBalance
  }

  func deposit(_ amount: Int) {
    balance += amount
    transactions.append(.deposit(amount))
  }

  func withdraw(_ amount: Int) throws -> Int {
    guard balance >= amount else { throw AccountError.insufficient }
    balance -= amount
    transactions.append(.withdraw(amount))
    return balance
  }
}

// 使う側
let account = BankAccount(initialBalance: 1000)

// ❌ 同期的にはアクセスできない
// print(account.balance)  // error: actor-isolated property

// ✅ await が必要
let current = await account.balance
await account.deposit(500)
let newBalance = try await account.withdraw(300)
要素class との違い
継承不可（final 相当。継承元として利用できない）
イニシャライザ同じ。init 内は await なしで状態を初期化できる
外部からのプロパティアクセスawait 必須。private でなくても外から書き込み不可（読み取り専用扱い）
外部からのメソッド呼び出しawait 必須（nonisolated なら不要）
内部からの自身へのアクセスawait 不要（同一アクター context 内）

Actor Isolation

Swift Concurrency の中核概念。各 actor は 独自の "isolation domain" を持ち、その内部状態にアクセスできるのは「その actor のメソッドの実行 context」だけ。 コンパイラはこのドメイン境界を静的に追跡し、違反をエラーにします。 

actor Library {
  var books: [String] = []

  // このメソッドは Library の isolation 内で実行される
  func addBook(_ title: String) {
    books.append(title)            // ✅ 同じ isolation
    let count = books.count       // ✅ 同じ isolation
  }

  // 別の actor を呼ぶには await が必要
  func syncWith(_ other: Library) async {
    let theirBooks = await other.books   // ✅ 別 isolation
    books.append(contentsOf: theirBooks)
  }
}

Isolation の 3 つのカテゴリ

分類意味例
Actor-isolated特定の actor のメソッド/プロパティactor.someMethod()
Globally isolatedGlobalActor で守られた宣言@MainActor func updateUI()
Nonisolatedどの isolation domain にも属さない普通の struct や func

Isolation = "プログラム内の島"

Actor isolation は「あの島の住人だけがあの島の物に触れる」というルール。島から島へ 荷物（データ）を渡すには await という"船"が必要で、 荷物自体は壊れずに運べる型（Sendable）でなければなりません。これを基本イメージにしてください。

なぜ await が必要なのか

初学者が必ず抱く疑問:「Int を 1 つ読むだけなのに、なんで await？」。 答えは「actor のメソッド呼び出しは "その actor のキューに並んで順番待ちする" 操作だから」。 キューに並んだ瞬間、自分のタスクは中断（suspend）され、他のタスクに CPU を譲ります。 これが await の意味です。

await = "今の actor を抜けて、相手の actor のキューに並ぶ" マーカー

キューに並ぶということは、すぐに実行できるとは限らないということ。だから他のタスクに CPU を譲るために await が必要。逆に「同じ actor 内のメソッド呼び出し」は キューに並ぶ必要がないので await 不要、という対称性があります。

nonisolated

actor のメソッドのうち「状態を読み書きしない」ものは nonisolated マークで isolation から外せます。 こうすると外から await なしで同期的に呼べるようになります。 

actor User {
  let id: UUID            // 不変なので nonisolated でも安全
  var name: String

  init(id: UUID, name: String) {
    self.id = id
    self.name = name
  }

  // id は immutable なので nonisolated にできる
  nonisolated var identifier: String {
    "user-\(id.uuidString)"
  }

  // CustomStringConvertible 適合のため nonisolated 必須
  nonisolated var description: String {
    "User(\(id))"     // id は OK
    // "User(\(name))"  ← name はエラー（actor-isolated）
  }
}

let user = User(id: .init(), name: "Alice")
print(user.identifier)   // ✅ await 不要

nonisolated の中では mutable 状態に触れない

nonisolated なメソッドの中で var プロパティを 読み書きしようとするとコンパイルエラー。コンパイラは「isolation を抜け出した瞬間に 可変状態へ触れたら data race の温床」と判断します。let 定数か、 別の actor へ await 経由でアクセスするなら OK。

Protocol 適合での典型用途

extension User: Hashable {
  nonisolated func hash(into hasher: inout Hasher) {
    hasher.combine(id)   // id は let なので OK
  }
  nonisolated static func == (lhs: User, rhs: User) -> Bool {
    lhs.id == rhs.id
  }
}

Hashable / Equatable / CustomStringConvertible のような同期的プロトコルに actor を適合させるとき、nonisolated はほぼ必須のテクニックです。

MainActor

@MainActor は Swift 標準で用意されている "メインスレッド専用の actor"。 UIKit / AppKit / SwiftUI の UI 操作は必ずメインスレッドで行う必要があるため、 これらの API は標準で @MainActor でマークされています。 

// クラス全体をメインアクター isolation に
@MainActor
final class SettingsViewModel: ObservableObject {
  @Published var theme: Theme = .light
  @Published var notificationsEnabled = true

  func loadSettings() async {
    // ここはメインスレッド
    let data = try? await SettingsAPI.fetch()
    // プロパティ更新もメインスレッドのまま → @Published 安全
    theme = data?.theme ?? .light
  }
}

// 個別のメソッドだけメインアクターに
final class DataLoader {
  func load() async -> [Item] {
    let items = await APIClient.fetchItems()
    await updateUI(with: items)
    return items
  }

  @MainActor
  private func updateUI(with items: [Item]) {
    // ここは確実にメインスレッド
    NotificationCenter.default.post(name: .itemsLoaded, object: items)
  }
}
使い所記述例
UI 全体@MainActor class ViewModel
特定メソッドだけ@MainActor func updateUI()
クロージャ内だけawait MainActor.run { ... }
SwiftUI Viewstruct MyView: View は暗黙的に @MainActor

SwiftUI ViewModel は @MainActor が定石

ObservableObject + @Published を使うとき、 プロパティ更新は メインスレッドからでなければなりません（さもないと UI 警告）。 class 全体に @MainActor を付けておけば、その心配が消えます。

GlobalActor

@MainActor は @globalActor 属性で実装された "メインスレッド版" にすぎません。同じ仕組みで「データベース専用 actor」「ログ書き込み専用 actor」 といったカスタムグローバル isolationが作れます。 

// Database アクセス用のグローバル actor を定義
@globalActor
actor DatabaseActor {
  static let shared = DatabaseActor()
}

// 使う
@DatabaseActor
final class UserRepository {
  private var connection: DBConnection

  func findUser(id: UUID) -> User? {
    connection.query(...)
  }
}

// 別ファイルでも DatabaseActor 経由で同じ isolation に乗せられる
@DatabaseActor
func cleanupOldRecords() async throws {
  // このグローバル actor 内のすべてが直列化される
}

レイヤー全体に "isolation の屋根" をかける

「永続化レイヤーは全部 DatabaseActor 上で動かす」「ログ書き込みは全部 LogActor で」 といった レイヤー単位の isolation 設計ができるのが GlobalActor の強み。 個別 actor を作るより、関心事をまとめやすい場合があります。

Sendable プロトコル

Actor の境界（isolation domain）を越えて受け渡せる型は Sendable プロトコルに準拠していなければなりません。コンパイラは isolation を越える代入や引数渡しを 検査し、Sendable でない型を渡そうとするとエラーにします。

型Sendable か理由
Int / String / Date✓ 自動値型で immutable
普通の struct (全プロパティ Sendable)✓ 自動値型で深くコピーされる
enum (associated value も Sendable)✓ 自動値型
final class + 全 let明示不変なので明示すれば OK
普通の class✗共有可変状態の温床
actor✓ 自動actor は本質的に Sendable
関数型 / クロージャ条件付き@Sendable 注釈が必要
 
// ✅ struct は自動 Sendable
struct Money: Sendable {
  let amount: Int
  let currency: String
}

// ✅ final class + let で明示
final class Logger: Sendable {
  let destination: URL
  // var は不可
}

// ⚠️ 共有可変 class — Sendable 不可
final class Cache {
  var entries: [String: Data] = [:]   // 可変
}
// → actor で包むか、@unchecked Sendable + 内部ロックを書く

// クロージャの @Sendable
func runLater(_ work: @Sendable @escaping () -> Void) {
  Task { work() }
}

@unchecked Sendable は最終手段

「コンパイラには見えないが、自分で排他制御するから安全」と宣言する逃げ口が @unchecked Sendable。手動ロックや DispatchQueue で守った class などで使われますが、正しさは 完全に開発者責任になります。可能なら actor に置き換える方が安全です。

Actor Reentrancy（再入可能性）

Swift の actor は 再入可能 (reentrant)。つまり「あるメソッドが await で中断している間に、同じ actor の別メソッドが実行される」 ことが起きます。これを知らないと、await の前後で見ていた状態が 変わっていて、不変条件（invariant）を破壊するバグを生みます。 

actor ImageCache {
  var cache: [URL: Image] = [:]

  func image(for url: URL) async throws -> Image {
    // ① キャッシュをチェック
    if let cached = cache[url] { return cached }

    // ② await で中断 — ここで他のタスクが actor に入ってくる！
    let image = try await downloader.fetch(url)

    // ③ 再開時、cache は ① で見たときと違う可能性がある
    //    別タスクが既に同じ url を入れているかも
    cache[url] = image   // 上書き → 同じ画像を 2 回 fetch している
    return image
  }
}

対策パターン: 進行中タスクを記憶する

actor ImageCache {
  var cache: [URL: Image] = [:]
  var inFlight: [URL: Task<Image, Error>] = [:]

  func image(for url: URL) async throws -> Image {
    if let cached = cache[url] { return cached }

    // 既に進行中なら、その Task の結果を待つ
    if let task = inFlight[url] { return try await task.value }

    // 自分が新規取得を担当する Task を登録
    let task = Task { try await downloader.fetch(url) }
    inFlight[url] = task

    defer { inFlight[url] = nil }
    let image = try await task.value
    cache[url] = image
    return image
  }
}

「await を挟んだら状態を読み直せ」が鉄則

await の前に確認した条件は、await の後では変わっている可能性がある。 これは Swift Concurrency の最重要ルールです。慣習的に「await の前後で必ず invariant を確認し直す」 と覚えておくと、Reentrancy バグの大半は防げます。

パフォーマンスと使い分け

actor は無料ではありません。メソッド呼び出しごとに「キューに enqueue → スケジューリング」のコストがかかり、 頻繁に呼ぶホットパスでは無視できないオーバーヘッドになることがあります。

用途適切な選択理由
共有される可変状態（キャッシュ、状態管理）actor並行アクセスが起きうる
UI 状態管理 (ViewModel)@MainActor classUI 更新は main thread 必須
不変データ (DTO, モデル)struct + Sendableコピーで十分
計算メソッドのみ (純粋関数)普通の func状態がない
1 タスク内の局所状態普通の class / struct並行アクセスがない
頻繁に呼ばれるホットループactor 化を再考キューイングコスト

「複数タスクから触られる可能性があるか」だけを基準にする

「並行アクセスが起きないなら actor 化は不要」が原則。1 つのタスクからしか触られない一時的な 状態（例: 1 リクエストのスコープ内だけで使うデータ）に actor を使うのは、安全性のためでなく 機械的に書いてしまっているだけ、ということがよくあります。

よくある落とし穴

実装でハマりやすいポイントを箇条書きで。レビューチェックリストとして使えます。

  1. await の前後で状態を読み直さない: Reentrancy で状態が変わっている可能性。条件分岐は await の後に再評価する。
  2. actor のメソッドを頻繁に呼びすぎる: ループで毎回 await すると遅い。バッチ化して 1 回の actor 呼び出しでまとめて処理する設計に。
  3. actor 内で長時間ブロッキング処理: 同じ actor の他のメソッドが全部待たされる。重い同期処理は Task.detached で別スレッドへ逃がす。
  4. nonisolated で var を触ろうとする: コンパイルエラー。本当に必要なら actor を分割するか、設計を見直す。
  5. @MainActor を class 全体に付けっぱなし: 計算メソッドまで全部 main thread になり UI が固まる。重い処理は別 actor / detached task に。
  6. 循環 await でデッドロックっぽい挙動: 厳密にはデッドロックしないが「actor A が actor B を await している間に B が A を await」で進行不能に近い状態に。設計レベルで避ける。
  7. @unchecked Sendable の濫用: 「とりあえず通す」ために使うと並行性バグの温床。actor で囲み直すのが本来。
  8. 非同期初期化が必要なケース: init は async にできない（Swift 5.5）→ Swift 5.7+ で可能だが、原則 factory メソッドにする方が見通しが良い。
  9. Swift 6 の strict concurrency: Swift 6 では Sendable / isolation 違反は全部エラー。Swift 5 系で -strict-concurrency=complete を有効にして段階的に移行。

覚えておく 1 行

「Actor の中の await は、外の世界に時間が流れることを許す境界」。 この一行を念頭に置くと、Reentrancy も Sendable も MainActor も、全部一貫して理解できます。
