Pages は 静的サイトの自販機である。

GitHub Pages はリポジトリの中身を HTTPS 配信する静的ホスティングサービス。 デプロイの仕組みは「Branch ソース」と「GitHub Actions ソース」の 2 種類。 何が起きるとサイトが更新されるのか、何が起きると失敗するのか、 内部で動く `actions/deploy-pages` の正体まで解説します。

無料 Public リポジトリ Pro 以上 Private リポジトリ 容量上限 1 GB 帯域 100 GB/月（ソフト制限）

GitHub Pages とは何か

GitHub Pages はリポジトリの中身を 静的サイトとして HTTPS で配信する無料サービス。 Public リポジトリならアカウントを問わず使え、Pro 以上なら Private リポジトリの内容も アクセス制限付きで配信できます。Jekyll などのビルドエンジンを通すこともできるし、 生の HTML/CSS/JS をそのまま置くこともできます。

提供2008無料サービスとして開始
配信FastlyCDN 経由
SSL自動Let's Encrypt
サーバ処理無しSSG / SPA 専用

動的処理は一切ない

Pages は完全に静的な配信のみ。PHP/Node などのサーバサイド実行はできず、 データベース接続も無理。ブラウザ JavaScript と外部 API へのリクエストのみで 完結する SPA / 静的サイト専用です。動的なものが要るなら Cloudflare Workers や Vercel へ。

2 つのデプロイソース

GitHub Pages には「コンテンツの取得元」が 2 種類あります。これがデプロイの仕組みを 理解する上で最も重要な分岐点。リポジトリ設定 Settings → Pages → Build and deployment → Source で 切り替えます。

① Deploy from a branch

指定したブランチ（main や gh-pages）の ルートまたは /docs フォルダを GitHub が自動的に拾って配信する。 push するだけでデプロイ。Jekyll 自動ビルドが走る。

② GitHub Actions 推奨

自分で書いた workflow が actions/deploy-pages 経由で artifact をアップロードして配信。ビルドプロセスを完全制御でき、 Vite / Next.js / Astro など任意のフレームワークが使える。

観点Branch ソースActions ソース
セットアップ最も簡単（クリック数回）workflow ファイル作成が必要
ビルドエンジンJekyll 固定 (or 無し)任意（Hugo, Vite, etc.）
カスタマイズ限定的完全自由
トリガーブランチへの push のみpush / schedule / dispatch / etc.
ビルド時間制限あり（10 分）Actions の枠（無料 2000 分/月）
デプロイ前のテスト困難同 workflow に組み込める

新規プロジェクトは Actions ソース一択

柔軟性・将来性ともに圧倒的。Branch ソースは「README.md だけ Jekyll で公開したい」 のような最小構成のときだけ価値があります。本ドキュメントの残りの大半は Actions ソース前提で書きます。

Branch ソースの内部

Branch ソースを選ぶと、内部では "pages-build-deployment" という GitHub 製の隠れワークフローが 勝手に走ります。Actions タブには表示されますが、ファイルとしては存在しません。

Branch ソース選択時の挙動

  1. 指定ブランチに push が起きると、pages-build-deployment ワークフローが起動。
  2. リポジトリのルート（または /docs）に _config.yml があれば Jekyll でビルド。なければ生の HTML をそのまま配信。
  3. ビルド成果物が GitHub Pages のサーバに配置され、Fastly CDN を経由して配信開始。
# Settings → Pages の設定例
Source:        Deploy from a branch
Branch:        main
Folder:        / (root)   # または /docs

Jekyll が勝手に動くと厄介な場合がある

ファイル名が _ で始まるディレクトリ（例: _data/）が Jekyll の規約で公開されないなどの罠がある。これを止めたい場合は リポジトリのルートに空の .nojekyll ファイルを置くと Jekyll 処理がスキップされ、ファイルがそのまま配信されます。

GitHub Actions ソースの内部

Actions ソースは 3 つの公式 actionで成り立っています。これらが順序通りに動くと Pages にデプロイされる、という固定の儀式があります。

最小構成の workflow

# .github/workflows/pages.yml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:        # 手動実行も可能に

permissions:                  # Pages デプロイには明示的な権限が必要
  contents: read
  pages: write
  id-token: write

concurrency:                  # 同時に複数走らせない
  group: "pages"
  cancel-in-progress: false

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Pages
        uses: actions/configure-pages@v5
        with:
          enablement: true     # Pages 未有効でも自動で有効化

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: '.'            # リポジトリ全体を配信

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
action役割キーポイント
configure-pagesPages 設定の取得・有効化enablement: true で自動有効化
upload-pages-artifact配信物を tar.gz にして artifact 化path で配信ルートを指定
deploy-pagesartifact を Pages サーバへ展開戻り値の page_url が公開 URL

何をするとデプロイされるか

Actions ソースの場合、デプロイのトリガーは workflow ファイルの on: セクションで 完全に決まります。GitHub Pages 自体には「自動的に push を見張る」機能はなく、 あなたが書いた workflow が起動条件を持つ仕組みです。

トリガー記述例用途
push on: push: branches: [main] main への push 直後に毎回デプロイ（最も一般的）
workflow_dispatch on: workflow_dispatch: Actions タブから手動でボタン実行
schedule on: schedule: - cron: '0 0 * * *' 毎日特定時刻に再ビルド（外部データ取り込みなど）
release on: release: types: [published] GitHub Release 公開時のみデプロイ
repository_dispatch on: repository_dispatch: 外部 API 経由で起動（Webhook 連携）

手動再実行のコマンド

# Actions タブから手動起動するのと同じ
gh workflow run "Deploy to GitHub Pages" --ref main

# 直近の run を確認
gh run list --limit 5

# 特定 run のログを見る
gh run view <run-id> --log

# 失敗ログだけ抽出
gh run view <run-id> --log-failed

"何を変更すると" デプロイされるか

push トリガーは ブランチに push があれば内容に関わらず起動します。 「README.md を直しただけ」でもデプロイが走ります。HTML ファイル変更時のみに絞りたければ on.push.paths: ['**/*.html', '**/*.css'] のように指定可能です。

workflow の重要パーツ

Pages デプロイ workflow には「これがないと動かない」セクションがいくつかあります。 コピペで動かしている人も多いですが、各部の意味を押さえておくとトラブル時に困りません。

permissions ブロック

permissions:
  contents: read       # コードの読み取り (checkout 用)
  pages: write        # Pages へのデプロイ権限
  id-token: write     # OIDC トークン発行 (Pages の認証に使用)

これを書き忘れると "Resource not accessible by integration" エラーでデプロイが失敗します。 一般的なワークフローでは contents: read がデフォルトですが、 pages: write と id-token: write は 明示的に許可しないと得られません。

concurrency ブロック

concurrency:
  group: "pages"
  cancel-in-progress: false

同名 group の workflow が同時に走らないようにキューイングする設定。 Pages サーバへのデプロイは 1 つずつ処理されるべきなので、これがないと 速い連続 push で奇妙なレースコンディションが起きます。 cancel-in-progress: false にしておくと、走行中のデプロイを 後発が中断しなくなり安全。

environment ブロック

environment:
  name: github-pages
  url: ${{ steps.deployment.outputs.page_url }}

"github-pages" は予約名で、Pages デプロイには必須。 url を設定すると Actions の UI に「サイトを開く」ボタンが出るのと、 Releases や PR にデプロイ URL が紐付くので便利。

URL の決まり方とカスタムドメイン

Pages の URL はリポジトリ名から機械的に決まります。User/Organization サイトと Project サイトでパターンが異なるのが少しややこしい。

種類リポジトリ名URL
User サイト <username>.github.io https://<username>.github.io/
Project サイト 任意の名前 (例: learnings) https://<username>.github.io/<repo>/
Organization サイト <org>.github.io https://<org>.github.io/

Project サイトの "サブパス問題"

<!-- ❌ 絶対パスはサブパスで壊れる -->
<link rel="stylesheet" href="/style.css">
// → https://user.github.io/style.css を見に行く（404）

<!-- ✅ 相対パス -->
<link rel="stylesheet" href="style.css">

<!-- ✅ サブパス込み (固定なら) -->
<link rel="stylesheet" href="/learnings/style.css">

Vite / Next.js などのフレームワークでは base 設定で対応します。 vite.config.js なら base: '/learnings/'。

カスタムドメインの設定

# 1. リポジトリ直下に CNAME ファイルを置く
echo "learnings.example.com" > CNAME

# 2. DNS で CNAME / ALIAS レコードを設定
#    learnings.example.com → branch10480.github.io

# 3. Settings → Pages で "Enforce HTTPS" をオン
#    (Let's Encrypt 証明書が自動発行)

制限事項

Pages は無料で使えますが、いくつかのソフト/ハード制限があります。 個人利用の範囲ではほぼ気にならないものの、知っておくと安心。

項目制限備考
リポジトリサイズ1 GB（推奨）超えると警告
公開後のサイトサイズ1 GB（ハード）超えるとデプロイ失敗
帯域100 GB/月（ソフト）超過時は CDN 制限がかかる場合あり
ビルド時間10 分（Branch ソース）Actions ソースは Actions の枠
デプロイ頻度10 回/時（推奨）超えるとレート制限
Public リポジトリ無料誰でも閲覧可
Private リポジトリPro 以上のみFree プランでは不可

商用・大規模配信には不向き

GitHub Pages は明示的に「商用 e コマースサイトを目的としたものではない」と TOS に書かれています。 ある程度のトラフィックを見込むサイトや、商用目的のサイトは Cloudflare Pages / Vercel / Netlify など CDN ホスティング専業サービスの方が安全。

よくある落とし穴

自分や他人がハマりがちな典型パターン。トラブル時はこのリストを上から見ていくと早い。

  1. Pages が有効化されていない: Settings → Pages で source が "None" のまま。configure-pages action の enablement: true で自動化可能。
  2. permissions が足りない: pages: write と id-token: write がないと "Resource not accessible" エラー。
  3. upload-pages-artifact の path 間違い: path: 'dist' と書いたのに build/ にビルドしている、など。
  4. サブパスでの絶対 URL: /style.css がサブドメインで 404。相対パスかフレームワークの base 設定で対応。
  5. Jekyll の自動処理: _data/ 等のフォルダが配信されない。.nojekyll ファイルでスキップ。
  6. ブラウザのキャッシュ: 「デプロイしたのに古いまま」は CDN ではなく Service Worker や HTTP cache。シークレットウィンドウで確認。
  7. HTTPS 証明書が出ない: カスタムドメインの DNS 浸透待ち（最大 24 時間）。CNAME が正しいか dig で確認。
  8. Workflow が 2 回走る: push と pull_request の両方をトリガーにすると、PR 時に同じ commit で 2 回起動。

この learnings リポでの実例

この learnings サイト自体が GitHub Pages 上で動いており、構築時に実際にハマったパターンが ありました。生きた教訓として記録しておきます。

起きた事象

  1. gh repo create branch10480/learnings --public --push でリポジトリを作成し、最初の workflow が起動。
  2. ところが Pages 設定がまだ "None" のままだったため、configure-pages@v5 が "Get Pages site failed. Not Found" でエラー終了。
  3. 後から gh api -X POST repos/.../pages -f build_type=workflow で Pages を有効化。
  4. すでに失敗した workflow はそのまま残り、サイトは未公開のまま。gh workflow run で手動再実行してようやくデプロイ成功。

学んだ教訓

# ❌ うちらが最初書いた pages.yml
- name: Setup Pages
  uses: actions/configure-pages@v5

# ✅ enablement: true を足すと、Pages 未設定でも自動で有効化される
- name: Setup Pages
  uses: actions/configure-pages@v5
  with:
    enablement: true

新規リポジトリでは enablement: true を必ず付ける

enablement: true を最初から書いておけば、Pages 設定なしの状態でも action 自身が GitHub API で Pages を有効化してから作業を続けます。 初回 push でいきなり成功する状態に持っていけるので、新規プロジェクトのテンプレートに 必ず含めておくのが正解。

デプロイ確認の最短ルート

# 直近の workflow 実行を見る
gh run list --limit 3

# 進行中のものを終わるまで watch
gh run watch <run-id> --exit-status

# サイトが本当に応答するか
curl -sI https://branch10480.github.io/learnings/ | head -3
# → HTTP/2 200 が返ってくれば成功

デプロイ成功 ≠ サイト反映

deploy-pages action 完了後、CDN への反映には 数十秒〜数分のラグがあります。「workflow は緑なのにサイトに変更が反映されない」と感じても、 まず 1〜2 分待ち、シークレットウィンドウや curl で実物を確認しましょう。
